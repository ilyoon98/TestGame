# 객체지향 원칙 정리

각 원칙이 무엇을 막아 주는지, 어떻게 판단하는지, 루치아(붕괴 통로) 코드에서 어디에 쓰였는지를 정리한다. AI에게 일을 맡길 때는 [실행 프롬프트](oop-development-prompt.md)와 함께 쓴다.

## 4대 특성

### 캡슐화: 상태와 그 상태의 규칙을 한곳에 둔다

- **역할:** 값이 엉뚱한 곳에서 바뀌어 규칙이 깨지는 것을 막는다. 규칙이 한 객체 안에 있으면, 규칙이 바뀌어도 고칠 곳이 하나다.
- **판단:** "이 값을 바꾸는 코드가 몇 군데에 있는가?"를 센다. 여러 곳이면 그 값과 규칙을 객체 하나로 모은다.
- **예:**
  - `BodyPart`는 내구도와 가드를 private 필드로 가진다. 가드는 `raiseGuard`로 큰 값만 남긴다.
  - `Fighter.healPart`는 부위 회복량만큼 전체 체력도 함께 올린다.
  - `OpeningView`는 오프닝 화면 단계와 튜토리얼 기록을 외부에 노출하지 않는다.
- **주의:** getter/setter만 붙이고 규칙은 바깥에 두면 캡슐화가 아니다.

### 추상화: 쓰는 쪽에는 "무엇을 하는지"만 보인다

- **역할:** 쓰는 쪽이 구현 세부에 묶이지 않게 한다. 구현을 바꾸거나 테스트용 가짜로 바꿔 끼울 수 있다.
- **판단:** 호출하는 코드가 상대의 내부 필드나 구체 클래스 이름을 알아야 하는가? 그렇다면 계약(메서드 이름과 의미)으로 줄인다.
- **예:**
  - `CardEffect`는 `apply`, `activate`, `ready` 세 메서드만 계약으로 가진다.
  - `HitModifier`는 `preview`와 `commit`, `Scheduler`는 `after`와 `cancel`, `Screen`은 `render`가 계약이다.
- **주의:** 구현이 하나뿐이고 바뀔 일도 없으면 추상 계층을 만들지 않는다.

### 상속: "~는 ~의 한 종류다"일 때만

- **역할:** 공통 행동을 한 번만 쓰고, 다른 점만 하위 클래스에서 바꾼다.
- **판단:** 하위 타입이 행동(메서드)을 바꾸는가, 값만 다른가? 값만 다르면 데이터로 구분한다. 상속은 두 단계를 넘지 않는다.
- **예:**
  - `Fighter → PartyMember → Nun·Companion`: 수녀는 칸이 3개이고, 쓰러지면 판이 끝난다.
  - `Enemy → TrainingDummy`: 쓰러지지 않는다.
  - `GuardEffect → CounterStanceEffect`: 가드를 올린 뒤 반격을 예약한다.
  - 간수·궁수·주술사는 능력치만 다르므로 하위 클래스 없이 `Companion` 하나와 데이터로 표현한다.
- **조합이 나은 경우:** 두 성질이 겹치면 상속으로 풀 수 없다. 벨보이 철문은 `Enemy`에 붙이는 `BellboyGate` 부품이다. 훈련용 벨보이도 철문을 가져야 하기 때문이다.

### 다형성: 종류를 묻지 않고 같은 메시지를 보낸다

- **역할:** `if(type===…)`, `switch(kind)`가 여러 파일에 퍼지는 것을 막는다. 새 종류를 추가해도 호출하는 쪽은 그대로다.
- **판단:** 같은 `switch`가 두 곳 이상에 있거나, 새 종류를 넣을 때마다 여러 파일을 고쳐야 하면 다형성으로 바꾼다.
- **예:**
  - `CardRegistry.of(id).activate(...)`는 공격·가드·회복·설치형 효과를 구분하지 않고 부른다.
  - 모든 전투원이 `interceptHit`을 가진다. 철문이 없는 적은 `NoGate`가 답한다.
  - `GameScreen`은 `game.phase`로 `Screen`을 찾아 `render`만 부른다.

| 원칙 | 막아 주는 문제 | 판단 질문 | 루치아의 예 |
| --- | --- | --- | --- |
| S 단일 책임 | 한 곳을 고치면 상관없는 기능이 깨진다. | 이 클래스가 바뀌는 이유가 하나인가? | 피해 계산(`DamageCalculator`)과 적용(`HitResolver`)을 나눴다. 전투 진행(`CooldownBattle`)과 타이머(`AutoBattleRunner`)도 나눴다. |
| O 개방-폐쇄 | 새 기능마다 기존 코드를 고쳐 회귀가 생긴다. | 새 종류를 등록만으로 추가할 수 있는가? | 피해 보정 8종이 각각 클래스이고, 순서는 `createHitModifiers` 목록으로 정한다. 새 효과는 `CardRegistry.register`로 넣는다. |
| L 리스코프 치환 | 하위 타입마다 호출부에 예외 처리가 생긴다. | 하위 타입을 넣어도 호출부가 그대로인가? | `TrainingDummy`는 `isDown()`이 항상 false이고 머리를 잃으면 회복한다. 전투 루프는 플래그를 보지 않는다. |
| I 인터페이스 분리 | 작은 기능이 거대한 객체 전체에 묶인다. | 필요한 협력자만 받는가? | `EnemyPlanner`는 카드 표와 `Party`만 받는다. |
| D 의존성 역전 | 규칙이 DOM·타이머·난수에 묶여 테스트가 어렵다. | 바깥 세계를 추상으로 받는가? | `AutoBattleRunner`는 `Scheduler`를 받고, 도메인은 시드 난수와 `StateEventSink`를 받는다. 테스트는 `ManualScheduler`를 넣는다. |

## 함께 쓰는 기법

- **조립 지점(Composition Root):** 객체 생성과 연결은 한 곳(`createGameServices`, 화면은 각 파일 끝의 인스턴스 생성)에서 한다. 그래서 누가 누구에게 의존하는지 한눈에 보인다.
- **교체 지점(seam):** 밸런스 도구가 옛 규칙을 바꿔 끼우는 다섯 곳은 `seams`로만 연결한다. 그 밖의 협력은 객체끼리 직접 참조한다.
- **얇은 위임 함수:** 예전 전역 이름(`render`, `hit` 등)을 쓰는 테스트·도구가 많으면, 이름을 한 줄짜리 위임 함수로 남긴 채 내부를 옮긴다. 호출부를 다 옮기면 지운다.
- **preview와 commit 분리:** 비교만 하는 계산은 상태를 바꾸지 않는다. 실제로 적용할 때만 일회성 보너스를 쓴다. 자동 표적이 같은 계산을 쓰면서도 상태를 망치지 않는 이유다.

## 클래스로 만들지 않아도 되는 것

- 상태도 협력자도 없이 값을 받아 HTML 문자열을 돌려주는 템플릿 함수(`bodyPanel`, `prepPanel` 등)
- 카드·적·지도 같은 선언형 데이터
- 한 곳에서만 쓰는 짧은 계산

객체지향은 모든 코드를 클래스로 바꾸는 일이 아니다. 상태와 그 상태의 규칙, 바뀔 수 있는 행동을 객체로 묶는 일이다.
