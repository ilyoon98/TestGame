# 객체지향 개발 실행 프롬프트

AI에게 기능 추가, 구조 개선, 리팩터링을 맡길 때 붙여 넣는 프롬프트다. 아래 "프롬프트" 블록을 통째로 복사하고, `{ }` 안을 채운다. 원칙별 역할과 판단 기준은 [객체지향 원칙 정리](oop-principles.md)에 있다. 루치아(붕괴 통로)의 실제 클래스 목록은 [CLASSES.md](../../prototypes/collapsed-passage/CLASSES.md)를 본다.

## 쓰는 때

- 새 규칙·적·카드·화면을 추가할 때
- 한 함수나 파일이 너무 많은 일을 할 때
- 전역 상태나 `switch` 분기가 늘어날 때
- 테스트하기 어려운 코드(DOM·타이머·난수에 직접 묶인 코드)를 고칠 때

버그 한 줄 수정이나 문구 수정처럼 구조와 상관없는 작업에는 쓰지 않는다.

## 프롬프트

````text
너는 이 저장소에서 객체지향 원칙으로 작업하는 개발자다.

[작업]
{무엇을 만들거나 고칠지 한두 문장}

[대상]
- 폴더: {prototypes/<실험 이름>/}
- 먼저 읽을 문서: 그 폴더의 AGENTS.md, ARCHITECTURE.md, CLASSES.md(있으면), docs/ai/oop-principles.md

[진행 순서]
1. 파악
   - 바꿀 동작이 지금 어느 클래스·함수에 있는지 찾는다. 추측하지 말고 파일과 줄을 확인한다.
   - 그 코드를 부르는 곳(테스트, QA 스크립트, 다른 폴더의 도구 포함)을 검색한다.
   - 지금 동작을 고정하는 테스트나 출력(기준선)을 찾고, 없으면 먼저 저장한다.
2. 설계 (코드를 쓰기 전에 짧게 보고한다)
   - 새로 만들거나 바꿀 클래스마다: 이름, 책임 한 줄, 가진 상태, 공개 메서드, 협력하는 객체.
   - 아래 [원칙 점검]을 한 줄씩 답한다. 해당 없으면 "해당 없음"이라고 쓴다.
   - 데이터로 충분한 것은 클래스로 만들지 않는다. 값만 다르면 데이터, 행동이 다르면 클래스다.
3. 구현
   - 한 번에 하나의 책임만 옮긴다. 단계마다 테스트와 기준선을 돌린다.
   - 기존 호출부가 많으면 예전 이름을 얇은 위임 함수로 남겨 두고, 호출부를 옮긴 뒤 지운다.
   - 게임 규칙(도메인)은 DOM, setTimeout, Math.random, localStorage를 직접 쓰지 않는다. 필요하면 생성자로 받는다.
   - 객체 생성과 연결은 조립 지점(예: createGameServices) 한 곳에서 한다.
4. 검증
   - 기존 테스트 전체, 새 단위 테스트, 저장한 기준선 비교, 실제 실행(브라우저 등)을 확인한다.
   - 확인하지 못한 항목은 이유와 함께 적는다.
5. 보고
   - 바뀐 파일, 새 클래스와 책임, 원칙 점검 결과, 검증 결과, 남은 일.
   - ARCHITECTURE.md와 CLASSES.md에서 바뀐 부분을 갱신한다.

[원칙 점검]
- 캡슐화: 상태를 바꾸는 규칙이 그 상태를 가진 객체 안에만 있는가? 바깥에서 필드를 직접 고치는 곳이 있는가?
- 추상화: 호출하는 쪽이 구체 클래스 대신 계약(메서드 이름과 의미)만 알면 되는가?
- 상속: is-a 관계인가? 두 단계를 넘지 않는가? 값만 다른데 하위 클래스를 만들지 않았는가?
- 다형성: 종류를 묻는 if/switch 대신 객체에게 같은 메시지를 보내는가?
- SRP: 이 클래스가 바뀌는 이유가 하나인가?
- OCP: 새 종류를 추가할 때 기존 코드를 고치지 않고 등록만 하면 되는가?
- LSP: 하위 타입을 상위 타입 자리에 넣어도 호출하는 쪽이 특별 처리를 하지 않는가?
- ISP: 필요한 협력자만 받는가? 거대한 상태 객체 전체를 넘기지 않는가?
- DIP: 시간·난수·화면·저장소를 추상(Scheduler, random 함수, 이벤트 싱크)으로 받는가?

[지킬 것]
- 결정성: 같은 시드와 상태는 같은 결과를 낸다. 난수는 시드 난수만 쓴다.
- 기존 테스트를 지우거나 기대값을 바꿔서 통과시키지 않는다. 바꿔야 하면 이유를 보고한다.
- 다른 폴더나 공용 설정은 작업에 직접 관련될 때만 고친다.
- 다른 세션이 같은 파일을 고치고 있으면 편집 전에 범위를 맞춘다.

[피할 것]
- 모든 함수를 클래스로 감싸기(상태도 협력자도 없는 템플릿 함수는 함수로 둔다)
- 깊은 상속, 다목적 Manager·Util 클래스, DI 컨테이너
- 쓰이지 않는 인터페이스나 미래를 위한 확장 지점
- 한 번에 여러 책임을 옮기는 큰 변경
````
